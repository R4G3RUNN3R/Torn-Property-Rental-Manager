# Property Rental Manager v0.4.0 Migration Checklist

This document is the deployment gate for moving v0.4.0 from GitHub to the live/hosted copy later. Do not deploy individual `src/` modules. Deploy the generated userscript only after the feature branch is verified.

## Release candidate

- Branch: `feature/v0.4.0-architecture`
- Pull request: `#14`
- Generated artifact: `R4G3RUNN3R-Property-Rental-Manager.user.js`
- Target version: `0.4.0`
- Production/main branch remains unchanged until the migration is explicitly performed.

## What changes

v0.4.0 consolidates the runtime architecture while preserving the v0.3.10 user-facing behavior.

The shipped runtime is built from stable module entries:

1. `property-core.js`
2. `market-core.js`
3. `api-core.js`
4. `draft-core.js`
5. `form-core.js`
6. `settings-core.js`
7. `update-core.js`
8. `ui-observer.js`
9. `app-runtime.js`
10. `bootstrap.js`

Historical `app-v*` sources remain in the repository as regression/migration fixtures for this release. They are not independent entries in the shipped module list.

## Persistent data compatibility

No intentional storage-key migration is required.

v0.4.0 preserves:

- the browser-local Torn API key setting
- UI/pricing settings
- update settings
- cached rental-market data
- saved property snapshots
- separate property/market checked timestamps

The migration must not clear localStorage as part of deployment.

## Pre-deployment verification

The GitHub branch must show all of the following before migration:

- `npm test` passes with zero failures
- `npm run check` passes
- `npm run build:check` passes
- generated userscript metadata reports `@version 0.4.0`
- package.json and package-lock.json both report `0.4.0`
- the release build contains `ui-observer.js` and `app-runtime.js`
- no versioned `app-v*.js`, `api-core-v*.js`, `ui-core-v*.js`, or `update-core-v*.js` is present in the shipped `sourceFiles` list
- stable runtime smoke test boots the controller successfully
- app UI observer test confirms one app-level native MutationObserver

## Live Torn smoke test

Before replacing any hosted/public copy, install the v0.4.0 generated userscript directly from the feature branch in a test Tampermonkey profile and verify:

1. Open Torn Properties.
2. Confirm the manager launches and only owned properties appear.
3. Confirm startup does not scan rental markets.
4. Confirm existing settings and saved API key state survive the upgrade.
5. Run SCAN MARKET on one property.
6. Confirm page/listing progress appears for a multi-page market.
7. Confirm Property checked and Market checked remain separate.
8. Cancel an in-flight scan and confirm Market checked does not advance.
9. Re-run the scan and confirm a valid quote is produced from exact upgrade matches only.
10. Change pricing basis and undercut and confirm the loaded quote recalculates without another market request.
11. Verify PREPARE RENTAL fills the correct 100-day values.
12. Alter a prepared Torn value manually and confirm LIST PROPERTY refuses to submit.
13. Re-prepare, then verify LIST PROPERTY performs one explicit native submission only.
14. For a `for_rent` test property, verify the staged cancellation flow requires explicit confirmation clicks.
15. Run UPDATE ALL and confirm property types are processed sequentially with visible global progress.

## Deployment

After the smoke test and GitHub verification pass:

1. Preserve the current v0.3.10 generated userscript as the rollback artifact.
2. Merge PR #14 only when the migration is being performed.
3. Use the generated `R4G3RUNN3R-Property-Rental-Manager.user.js` from the verified commit.
4. Replace the hosted/public userscript atomically where possible.
5. Do not copy individual source files to the live location as a partial deployment.
6. Confirm the live copy reports `@version 0.4.0`.
7. Repeat the short live smoke test: launch, owned-property sync, one SCAN MARKET, PREPARE RENTAL verification.

## Rollback

If the live smoke test exposes a regression:

1. Restore the preserved v0.3.10 generated userscript.
2. Do not clear browser-local settings or snapshots.
3. Record the failing v0.4.0 commit and exact Torn action that reproduced the issue.
4. Re-open/fix the feature branch rather than patching the hosted generated file by hand.
5. Re-run the full GitHub verification and smoke-test gate before attempting migration again.

## No server-side data migration

This project does not require a database schema migration for v0.4.0. The release is a userscript/runtime architecture change. Any future hosting move should treat the generated userscript as the deployable artifact and keep unrelated databases/services isolated.
